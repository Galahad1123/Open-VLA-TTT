# RoboTTT 更新时机与隐藏特征：首版选择及研究问题

日期：2026-10-05。状态：用户已确认首版选择；下列风险与消融尚未得到本项目实验验证。

关联：[架构约定](2026-10-01-ttt-research-architecture-notes.md)、[实施设计](2026-10-05-evo1-groot-robottt-design.md)。本记录将实现选择与待研究问题分开，避免把未经验证的改造混入首版 RoboTTT。

## 首版决定

1. **隐藏特征按论文描述接入。** 每个指定 attention 子层后的完整 register/state/action token 表示参与 TTT；不将动作部分限制为已执行的前缀，也不另加独立的“安全写入”前向。VL tokens 通过 cross-attention 影响这些表示，不直接送入 TTT。
2. **去噪累计更新沿用已读社区实现。** 每次去噪调用都基于上次返回的 fast weights 继续更新，最终状态延续至下一次动作决策；不在各去噪步骤间恢复同一个历史快照。
3. **明确来源边界。** 第一项有论文结构描述依据；第二项是用户选择的社区工程协议，不能表述为已核实的官方去噪状态协议。参考代码中的重复残差等已识别实现问题不因此被采纳。
4. **问题保留为研究对象。** 暂不以已执行前缀写入、非重叠 chunk 或模型生成历史替换上述机制；后续通过记录、诊断与消融评估。这不代表已证明重叠监督无风险，也不代表阶段 B 已验收。

## 一、TTT layer 在什么时机更新

论文 §3.1–3.2 描述在 attention 后加入 TTT，每个轨迹位置执行 update-then-apply，episode 从学习到的 W0 开始，动作通过多步去噪生成。文字没有明确列出每个去噪步骤之间的 fast-weight 状态交接协议。

社区固定版本的 `_forward_with_ttt()` 在 hook 中读取 `layer_fast_weights[idx]`，调用 wrapper 后立即用返回状态替换它。因此，当挂载模块在底层采样的去噪循环中反复执行时，更新会累计。wrapper 的状态计数也随调用处理的序列位置推进。

对我们采用的逐次累计协议，单个 TTT 层的状态流为：

```text
上一动作决策的最终状态
  → 去噪调用 0：更新、读取
  → 去噪调用 1：继续更新、读取
  → ...
  → 去噪调用 K-1：继续更新、读取
  → 下一动作决策
```

这发生在动作生成过程中，并不是先执行动作前缀、再使用实际执行结果更新。episode reset 恢复初始状态；推理所需的 detach 只截断梯度，不清空记忆数值。

需要记录和验证：

- 在每层每次去噪恰好调用一次的实现中，单个动作决策对应每层 K 次更新；额外前向、预热或重算不应被漏记。
- 环境步、动作决策步、去噪步、记忆更新计数和 RoPE 位置索引分别定义，不能将它们都叫作同一个 `step`。
- 论文的 Sequence Action Forcing 及社区训练入口每个轨迹位置采样一个噪声等级；这不等同于训练时展开 K 次部署去噪。首版保留该配方差异并记录，不声称训练与部署更新次数相同。
- 改变 K 同时改变生成精度、计算量和记忆更新次数。后续去噪步数消融不能只归因于某一个因素。

## 二、TTT 更新使用哪些隐藏特征

论文的输入组织可概括为：

```text
register tokens + state token + 完整 noisy action chunk tokens
  → 当前时刻的 self/cross attention
  → 隐藏特征 X
  → Q/K/V 投影
  → 以 f_W(K) 拟合 V，更新 W
  → 用更新后的 W 读取 Q，经门控融合
```

在本项目预测 horizon=50 的配置下，动作部分包含全部 50 个位置的表示；执行前缀为 10 不会自动将 TTT 输入缩减为 10 个动作位置。实际输入还包含 registers 和 state，并非仅有 50 个 action tokens。

| 阶段 | action token 的来源 | 是否等于已执行动作 |
| --- | --- | --- |
| 训练 | 完整真实动作 chunk 的加噪版本 `τA+(1−τ)ε` | 不等于只使用当前决策前已执行的动作 |
| 推理 | 当前去噪迭代的动作估计 | 属于模型生成中的计划，不是未来真实标签或执行反馈 |

社区 `TTTWrapper`、`MemoryKeyValueBind` 提供可选的 `select_tokens_slice`，默认 `None`；默认处理挂载位置输出的全部 tokens。该切片没有自动关联机器人执行 horizon。若上游 attention 已混合完整 chunk，仅在 TTT 入口截取前 10 个 action tokens 或 registers，也不保证消除其他动作位置的信息。

## 三、teacher forcing、重叠 chunk 与信息路径

训练使用真实历史输出、推理使用模型历史输出，具有 teacher-forcing 性质；当前真实动作加噪用于 flow matching 本身则是正常的去噪监督，不能一概称为泄漏。

需要单独审计的情形是：**训练 stride 小于预测 horizon，并将含有真实 chunk 信息的记忆跨位置传递。** 例如训练位置为环境时刻 0、10，而每个 chunk 长 50：

| 训练位置 | 真实 chunk 覆盖范围 | 对后继位置的含义 |
| --- | --- | --- |
| 0 | 动作 0..49 | attention/TTT 状态可能携带整个范围的标签信息 |
| 10 | 动作 10..59 | 继承的历史可能已经含有目标区间 10..49 的信息 |

这是需要实验检查的潜在目标捷径和训练/部署差异，不是已经测得的性能问题。推理中记住此前预测的完整动作计划，并不等于读取未来真实动作；两者不能混淆。加噪、更多更新、loss mask 或 detach 均不能单独证明上述标签路径不存在。

**证据限制：** 当前核对的论文与通用社区 wrapper 不足以唯一确定官方预测 horizon、执行 horizon、训练 stride 和机器人执行调度的完整组合。50/10 是本项目的控制配置，不应当作论文公开的参数。不能据此断言官方实验或所有社区使用方式存在泄漏。

## 四、后续诊断与消融

首版先建立论文机制与所选社区协议的可运行参照，明确报告实际 horizon、stride、执行前缀、噪声分布与更新次数，再考虑以下实验：

- **更新时机：** 逐去噪累计，与同一历史快照计算候选/决策边界提交的变体比较；报告计算与更新预算。
- **隐藏特征：** 完整 token 集合、register-only、动作前缀等变体；注明在 attention 前还是后限制信息，后者不等价于前者。
- **历史来源：** 真实加噪 chunk、模型生成的历史、仅保留已执行部分的独立写入路径；分别报告配方变化与额外计算。
- **重叠诊断：** 固定当前位置的去噪输入与随机数，只扰动历史 chunk 中覆盖当前/未来目标的标签，观察历史状态与当前输出的变化。对首版，这是用于量化信息路径的诊断，不预设必须无变化；不能将该诊断包装成已经通过的“无泄漏”保证。
- **基本因果性测试：** 修改序列中更晚位置的输入，不得改变较早位置的输出。这与上一项历史 chunk 内的标签重叠诊断是不同问题，应分别测试。

本文件只记录决定与研究问题，不要求当前实现所有消融，也不修改正在训练的无记忆 baseline。
