## 代码与验证

- 两个阶段各启动一个 torchrun 作业，使用 LeRobot Accelerate/DDP，阶段结束后释放进程。
- batch_size为每卡batch；steps为同步优化器更新数。固定steps与chunks_per_task互斥。
- rank0创建运行记录/保存检查点；记录world_size与全局batch，同阶段恢复禁止改变它们。
- 任务均衡全局样本流由Accelerate分片。修复恢复epoch被DataLoaderShard重置为0的问题；
  DDP最后不满batch从原epoch前缀补齐，恢复不会改用恢复位置的前缀。
- 新增测试先复现缺失行为/恢复错误，再通过修复；目标测试15项通过。
- 完整CPU套件301 passed、7 skipped、18条已有torch.jit弃用警告；ruff/diff检查通过。
  首次沙箱运行因CLI未加入PATH和本地socket权限有7项失败；修正运行环境后整套通过。
- 独立代码审查发现的跨epoch恢复问题已修复。真实GPU短测覆盖epoch0恢复；跨epoch和padding
  的采样一致性由真实Accelerate prepare_data_loader的CPU回归测试覆盖，不声称GPU训练逐bit恢复。

所有路径均以 `/root/autodl-tmp/outputs` 为根：

| `ddp-batch3-20261028/` | 每卡4个worker，两个阶段各40步，batch8/3 |

各运行的检查点位于对应的 `<run-name>-stage1` / `<run-name>-stage2` 目录。
短测每20步保存，正式配方每5000步保存。短测warmup=1、总步数=40，与正式学习率曲线不同；
loss下降只能证明优化链路能工作，不能用于判断正式训练收敛或任务成功率。

测试调用模式：

```bash
CUDA_VISIBLE_DEVICES=0,1 NCCL_P2P_DISABLE=1 NCCL_IB_DISABLE=1 OMP_NUM_THREADS=4 \
bash scripts/train_rmbench_multi.sh \
  --machine configs/machine.local.toml \
  --recipe configs/training/rmbench/all-80k.json \
  --tasks all --num-processes 2 --run-name ddp-prefetch-20261028 \
  --smoke-steps 40 --smoke-use-recipe-batch --num-workers 4
```

同阶段恢复保留上述参数，增加 `--stage stage2 --resume <000020/pretrained_model>`。
缓存/临时目录环境变量见 [跨机器快速开始](../portable-training.md#双卡与固定-80k-更新预算)。

## 结果与预算建议

四轮均正常退出（exit0）；无NaN/OOM。原始GPU/日志采样及每轮 `summary.json` 保留在上述远端目录。
本机汇总位于 `artifacts/experiments/rmbench-ddp-20261028/remote-summary.json`。
恢复测试实际执行第21–40步，日志确认恢复epoch0、全局sample160，检查点保存step40/num_processes2/batch4。

下表为每阶段第6–40步 `updt_s + data_s` 的中位数；显存来自nvidia-smi的进程运行期间采样，
不同于训练logger的PyTorch分配内存，不保证捕捉亚秒级瞬时峰值。

| 配置 | Stage1 每卡batch / 秒每步 | Stage2 每卡batch / 秒每步 | Stage2 每卡显存 | 80k更新外推（均值） |
|---|---:|---:|---:|---:|
| 4个worker，batch4 | 8 / 0.641 | 4 / 1.323 | 19.37 GiB | 28.73 h |
| 4个worker，batch3 | 8 / 0.641 | 3 / 1.072 | 18.64 GiB | 23.66 h |

无worker时 Stage1/Stage2 每步中位数约3.51/2.79秒，主要是同步读图，不能当作正式训练速度。
启用预取后Stage2读图等待约0.002秒，计算/通信成为主要耗时。

**建议本次双4090的24h左右实验使用 `all-80k-batch3.json`**：Stage1 5k×全局batch16，
Stage2 75k×全局batch6，每5k保存。实测均值外推23.66h；加上初始化、保存和长时间波动，
建议按约24–25h安排，短测不能保证硬性的24h截止。原batch4配方仍可用，预算约29h。
每卡batch3在75k更新中共训练45万个chunk，较batch4的60万个减少25%；这是时间/样本预算权衡，
并不是证明较小batch具有更好收敛效果。

正式训练可用如下命令（先按快速开始设置数据盘缓存环境变量）：

```bash
cd /root/Open-VLA-TTT
CUDA_VISIBLE_DEVICES=0,1 NCCL_P2P_DISABLE=1 NCCL_IB_DISABLE=1 OMP_NUM_THREADS=4 \
bash scripts/train_rmbench_multi.sh \
  --machine configs/machine.local.toml \
  --recipe configs/training/rmbench/all-80k-batch3.json \
  --tasks all --num-processes 2 --num-workers 4 \
  --run-name rmbench-all-80k-ddp-batch3-seed1000
```

测试结束时双卡均已释放（各1MiB、利用率0%）。系统盘仍13G/30G（43%）；数据盘124G/328G，
剩余约205G。测试共保留三组各两阶段的20/40步完整检查点（约60GiB）以及小型日志，
另有约33GiB可复用的数据缓存；它们均在数据盘。正式训练未启动。
